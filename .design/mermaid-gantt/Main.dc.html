Mermaid support, and the one gap
Six notations convert both ways. Gantt reads Mermaid but will not write it — the only kind with an emit gap, and it is a decision rather than an omission.
NotationImportEmitStanding
C4yesyesTwo-way. Export is lossy and says so — MERMAID_C4_EXPORT_CAVEAT names what is dropped.
SequenceyesyesTwo-way.
FlowchartyesyesTwo-way; import refuses unsupported shapes by name.
Use caseyesyesTwo-way; Mermaid has no use-case type, so import is a lossy read.

TimelineyesyesTwo-way.
Ganttyesno — by decisionNo gantt-emit.ts, and the mapping says it must not grow one. Two things a gantt says have no Mermaid spelling — below.
Dictionary——No converter. Mermaid has no equivalent notation.
Lifecycle——No converter built.
01
at-risk has no tag
Our states are planned · active · done · at-risk. Mermaid's are done · active · crit plus milestone. The nearest to "in flight and in trouble" is active, so an emit turns the amber bar blue and tells nobody.
Verdict: ordinary loss. The repo already ships this shape — a named caveat, as C4 does.
02
The critical path is computed
Ours falls out of the float pass and cannot be authored — no crit keyword in the grammar, and critical lives only on the laid-out item, never on the model. Mermaid's crit is a word someone types.
Verdict: not loss — integrity. Emitting it turns arithmetic into a claim the next editor can falsify.
Where the rule may be over-strict. The two halves are not the same kind of problem. C4 exports lossily and names the loss; flowchart and use case emit despite lossy imports. A middle exists: emit done/active/milestone, never write crit, and state both facts in a caveat. That keeps 02's integrity argument intact while ending the blanket refusal — but relaxing it is your call, not the code's.
